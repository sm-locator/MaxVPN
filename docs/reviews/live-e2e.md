# Настоящий сквозной тест MaxVPN

Выполнен 12 ноября 2026 в отдельной копии PR #2. Используются настоящий Chromium,
React, FastAPI, PostgreSQL 17, SSH, appliance и три OpenWrt VM. Сценарии не
перехватывают API и не подменяют результаты команд роутера. Итоговый проход
обоих сценариев с дополнительной проверкой трафика завершился за **49,6 с**.
Он использовал заново созданную PostgreSQL и отдельные overlay, подготовленные
в этом прогоне. До запуска исправлены зависимости и UCI-фикстура стенда.
Проверки и контрольные суммы: [live-e2e-evidence.json](live-e2e-evidence.json).

## Воспроизведение

Нужны Linux, Docker, QEMU/KVM, Node 22, зависимости frontend и Playwright Chromium,
Python с backend-зависимостями и три образа из `openwrt-lab.md`. Checkout не
должен содержать `.env` в корне или backend. Фиксированный loopback-порт 4179
должен быть свободен. Остальные порты и секреты создаются отдельно для стенда.

```bash
PYTHON=/path/to/test-venv/bin/python
STATE=/tmp/maxvpn-live-e2e-fresh
"$PYTHON" scripts/live_e2e.py --state "$STATE" --python "$PYTHON" start
"$PYTHON" scripts/live_e2e.py --state "$STATE" test
"$PYTHON" scripts/live_e2e.py --state "$STATE" stop
```

`start` создаёт новые overlay, устанавливает актуальные исходники, одноразовые
SSH-ключи и сервер VLESS в отдельной WAN VM. Если в существующем образе OpenWrt
21.02.7 x86-64 нет curl или поддержки ipset в dnsmasq, хост скачивает настоящие
пакеты из официального архива, проверяет SHA-256 по индексу и копирует их по SSH.
Перед заменой dnsmasq сохраняется и восстанавливается конфигурация DHCP этого
стенда. Для другого образа зависимости должны быть подготовлены заранее.
Гостям не предоставляется доступ в Интернет.

PostgreSQL использует отдельный контейнер и tmpfs; порт опубликован только
на loopback. Применяются настоящие миграции. FastAPI получает отдельные ключи
JWT и Fernet и подключается к VM через настоящий SSH со строгой проверкой
ключа хоста. Локальный wrapper задаёт только SSH-конфигурацию этого стенда.
Vite проксирует API в этот backend. Управление и LAN/WAN разделены.

На итоговом стенде подтверждено сохранение `assets.example.test` →
`203.0.113.40` в PostgreSQL. CIDR `203.0.113.30/32` присутствует в static ipset,
а DNS-адрес — в динамическом ipset. HTTP из LAN к обоим адресам проходит при
включённом локальном VLESS; HTTP к непомеченному `203.0.113.10` проходит через
туннель. В сохранённых окнах pcap — 0 непомеченных тестовых IPv4/IPv6-пакетов.
После завершения все процессы и контейнеры обоих live-стендов остановлены.

`test` сбрасывает только правила одноразового роутера к исходной фикстуре.
Для полного повторения bootstrap и смены пароля нужен новый `STATE`: сценарий
меняет одноразовый пароль администратора. `stop` завершает только процессы
с маркером этого стенда, его VM и контейнер; логи, pcap и overlay остаются.
Ключи, токены, трассы браузера и конфигурации стенда не добавляются в Git.

## Что проверяется

1. Первый администратор создаётся через интерфейс. Импортированный VLESS-профиль
   доступен после повторного входа, в обычном списке нет UUID подключения,
   экспорт владельца расшифровывает профиль. Проверка самой PostgreSQL сравнивает
   ciphertext и расшифрованное значение с одноразовым UUID.
2. Правило CIDR создаётся, выключается и включается через интерфейс. Реальный
   LAN-клиент делает DNS-запрос к роутеру; роутер пересылает его отдельной WAN VM.
   Диагностика читает настоящие ответы dnsmasq и сохраняет выбранный домен.
3. Интерфейс отправляет правила в appliance и применяет их. Проверяются
   mangle/ipset, policy route и совпадение сохранённого и применённого хешей.
   Дополнительный проход проверяет созданные браузером CIDR/DNS-исключения в
   реальных ipset, HTTP из LAN по этим исключениям рядом с VLESS и отсутствие
   непомеченного IPv4/IPv6 трафика в захвате WAN. Положительный контроль в WAN
   подтверждает работоспособность захвата. DNS-ответ сохраняется фоновым backend.
4. Обычный пользователь получает `403` на общие управляющие операции,
   `404` на чужое правило, видит только свои профили и может менять свои правила.
5. Смена пароля без смены email отзывает старый JWT. Повторный вход новым паролем
   работает. Для проверки истечения локальный помощник подписывает одноразовый
   токен с прошедшим сроком; реальный backend возвращает `401`, панель завершает
   сессию и позволяет снова войти. Ответ API не перехватывается.

## Границы

Локальный peer использует поддерживаемый plain VLESS. Смена сетевого режима
в дополнительной проверке трафика выполняется лабораторной фикстурой через serial,
а не кнопкой выбора VPN в браузере. Импортированный браузером профиль не
используется для проверки REALITY/автовыбора серверов. AmneziaWG отложен пользователем.
Внешние DNS/DoH/TLS/URLTest и GL.iNet/аппаратный Brume 3 этим тестом не сертифицированы.

Первый живой прогон выявил несовместимость прежнего backend Apply с appliance
Push: он вызывал другой механизм сохранения runtime, получал `500` и оставлял
static ipset отсутствующим. Теперь применяется снимок appliance; проверяются
ошибки, устаревший fingerprint и отсутствие повторов изменяющего запроса.

Live-сценарии запускаются отдельно от обычного CI из-за требований к VM/образам.
В CI остаются все backend/appliance-тесты и 6 браузерных сценариев отказов с
управляемыми ответами API. Локальный live backend использует Python 3.14;
основной набор и CI используют Python 3.12 с зависимостями контейнера.
