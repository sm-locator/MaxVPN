# Проверка обновления и восстановления PostgreSQL

`make test-docker` перед обычными тестами выполняет два прогона обновления
PostgreSQL 17 с данными. Compose создаёт отдельную внутреннюю сеть и временную
базу в tmpfs, не публикует порт и не читает рабочий `.env`.
Тестовые контейнеры работают с UID/GID запускающего пользователя, чтобы
закрытые временные снимки были доступны и локально, и на CI runner.

| Исходная схема | Данные |
| --- | --- |
| `c5c9faf426ba`, head миграций `main` (`80988a9`) | Администратор и пользователь, серверы, связанные клиенты и глобальные WireGuard-клиенты; разные enabled, NULL PSK. Профилей и правил в этой схеме ещё нет. |
| `2a6f19c4b8d1` | Те же записи, AWG- и VLESS-профили с зашифрованными конфигурациями, IPv4/IPv6 CIDR и доменные правила, группы зависимостей и их связи. |

Для каждого состояния стенд:

1. Снимает снимок всех таблиц, существующих столбцов, значений и последовательностей ID.
2. Создаёт логический backup через `pg_dump --format=custom`.
3. Применяет `alembic upgrade head` и сравнивает все прежние данные.
4. Восстанавливает backup через `pg_restore --exit-on-error` в другую базу,
   проверяет точное восстановление старого состояния, затем повторяет обновление
   и проверку сохранности данных.

Снимки и дампы находятся только в закрытом временном каталоге и удаляются при
завершении. В журнал выводятся имена таблиц и количество строк, без значений.
Проверка ограничивает адрес базы сервисом `database` и именами тестовых баз;
произвольный URL рабочей базы она не принимает.

Для дополнительной проверки сохранённого локального дампа:

```bash
MAXVPN_UPGRADE_DUMP=/absolute/path/to/backup.dump make test-docker
```

Исходный файл читается, а восстановление и обновление выполняются внутри того же
одноразового окружения. В прогоне 11 ноября использован локальный дамп
`maxvpn-pre-vless-20261014-225851.dump` со схемой `0ffda25442bd`.
Он не добавлен в репозиторий и не передавался в GitHub. Это сохранённая копия,
а не снимок текущей рабочей базы.

В сохранённом дампе проверены 2 пользователя, 2 AWG-профиля, 51 правило,
3 группы и 5 связей групп. Таблицы клиентов и серверов там пусты, поэтому
сохранность непустых записей этих типов проверялась синтетическими данными.
В синтетической схеме с VLESS проверены по 2 записи каждого вида профилей,
6 правил, 2 группы и 2 связи. Значения зашифрованных конфигураций сравниваются
побайтно; это не проверка расшифровки реальных профилей без отдельного ключа.

## Процедура выпуска

Эти шаги предназначены для отдельного согласованного обновления, которое в
рамках PR не выполнялось:

1. Остановить запись приложений и фоновых процессов. Сохранить версию исходного
   кода, значение `alembic_version`, версии PostgreSQL и расширений.
2. Создать `pg_dump -Fc` PostgreSQL. Отдельно сохранить защищённую копию ключа
   шифрования VPN-конфигураций, настроек и SQLite/data appliance. PostgreSQL-дамп
   не содержит ключ шифрования и файлы роутера.
3. До обновления восстановить дамп в отдельную совместимую PostgreSQL с помощью
   `pg_restore --no-owner --no-privileges --exit-on-error`. Проверить данные,
   связи, роли и расшифровку профилей с сохранённым ключом. Проверка `--no-owner`
   требует заранее назначить владельца/права целевой роли; роли и права кластера
   этой проверкой не восстанавливаются.
4. Прогнать обновление на восстановленной копии. Затем применить миграции при
   остановленных записях в согласованном окружении и проверить вход, профили,
   клиентов и правила. Сохранить backup до завершения проверки.
   Версия JWT теперь связана с текущим хешем пароля: пользователям потребуется
   войти заново. Смена пароля отзывает ранее выданные токены, включая случай,
   когда email не изменился. Управление общим роутером и LAN-диагностика требуют
   роли администратора; собственные профили и правила остаются доступны владельцу.
5. Для отката остановить новую версию, восстановить backup в чистую отдельную
   базу и вернуть соответствующую старую версию приложения и её настройки.
   Повторно проверить данные перед переключением. Автоматический downgrade
   новых схем не заменяет восстановление backup; несколько VLESS-профилей
   несовместимы со старым ограничением на один профиль.

Проверка доказывает сохранность SQL-данных и работоспособность логического
backup/restore для рассмотренных состояний. Она не заменяет проверку свежей
копии перед реальным обновлением, ключей, внешних файлов, расширений и прав
конкретного рабочего кластера.
