# Non-Functional Requirements

**Version:** 1.0 Draft

**Status:** Architecture Specification

**Applies to:** MaxVPN v0.3+

---

# Purpose

Настоящий документ определяет нефункциональные требования к Policy Engine.

Эти требования не описывают функциональность системы.

Они определяют требования к качеству реализации.

---

# Design Principles

Policy Engine проектируется как независимое доменное ядро.

Архитектура должна обеспечивать:

- простоту сопровождения;
- расширяемость;
- тестируемость;
- предсказуемость;
- производительность.

---

# Deterministic Behaviour

Policy Engine обязан быть полностью детерминированным.

При одинаковом:

- Routing Request
- Rule Set

результат всегда должен быть одинаковым.

Использование случайности запрещено.

---

# Stateless

Policy Engine не хранит внутреннее состояние.

Он не использует:

- глобальные переменные;
- кэш состояния;
- пользовательские сессии.

Каждый запрос обрабатывается независимо.

---

# Pure Decision Making

Policy Engine не изменяет входные данные.

Он не изменяет:

- Rule Set
- Routing Request

После завершения работы состояние системы остаётся неизменным.

---

# Infrastructure Independence

Policy Engine не должен зависеть от:

- FastAPI
- SQLAlchemy
- PostgreSQL
- Linux
- WireGuard
- AmneziaWG
- Docker
- Web UI

Ядро должно быть переносимым.

---

# Testability

Каждый компонент должен тестироваться изолированно.

Для тестирования Policy Engine не требуется:

- база данных;
- файловая система;
- сеть;
- VPN.

Все зависимости должны подменяться.

---

# Extensibility

Добавление нового:

- Condition;
- Policy;
- Executor;

не должно требовать изменения существующих компонентов.

Расширение системы предпочтительнее модификации.

---

# Predictability

Порядок обработки правил всегда одинаков.

Никакая оптимизация не должна изменять результат вычислений.

---

# Performance

Policy Engine должен эффективно работать с большим количеством правил.

Оптимизация алгоритмов допускается только при сохранении внешнего поведения.

---

# Readability

Исходный код должен быть максимально понятным.

Предпочтение отдаётся:

- простым алгоритмам;
- небольшим классам;
- понятным именам.

---

# Maintainability

Каждый компонент должен иметь одну ответственность.

Сложность методов должна оставаться минимальной.

Большие классы необходимо разделять.

---

# Modularity

Каждый модуль должен иметь минимальное количество зависимостей.

Связность между модулями должна быть низкой.

---

# Reliability

Ошибки одного компонента не должны нарушать работу остальных компонентов системы.

Policy Engine обязан корректно сообщать об ошибках вызывающему коду.

---

# Scalability

Архитектура должна поддерживать рост без изменения существующего ядра.

Рост возможен за счёт:

- новых Conditions;
- новых Policies;
- новых Executors.

---

# Documentation

Каждая публичная сущность должна иметь описание.

Архитектурные решения должны быть отражены в документации проекта.

---

# Coding Standards

Проект придерживается следующих требований.

- Ruff
- Black
- Type Hints
- TDD
- SOLID
- Clean Architecture

Все новые изменения должны соответствовать данным требованиям.

---

# Backward Compatibility

Расширение функциональности не должно нарушать работу существующих правил.

Если нарушение совместимости неизбежно, оно должно сопровождаться миграцией и быть отражено в Release Plan.

---

# Security

Policy Engine не должен выполнять произвольный код.

Все входные данные должны считаться недоверенными.

Валидация выполняется до передачи данных в Policy Engine.

---

# Future-Proof Design

Архитектура должна предусматривать возможность появления:

- нескольких VPN;
- нескольких Executor;
- групп устройств;
- профилей;
- новых типов условий;
- новых типов политик.

При этом существующее ядро не должно требовать переработки.

---

# Quality Goals

При разработке Policy Engine приоритеты располагаются следующим образом.

1. Correctness
2. Predictability
3. Simplicity
4. Testability
5. Maintainability
6. Performance

Производительность никогда не должна достигаться ценой корректности или читаемости архитектуры.

---

# Architecture Rule

Если новая функциональность требует изменения фундаментальных принципов Policy Engine, это считается архитектурным изменением, а не обычной доработкой.

Такие изменения должны обсуждаться отдельно и сопровождаться обновлением архитектурной документации.

# Evolution Strategy

Приоритет развития проекта следующий:

1. Сохранить простоту архитектуры.
2. Не нарушить существующие инварианты.
3. Добавить новую возможность расширением.
4. Изменять существующее ядро только при отсутствии другого решения.

Архитектура проектируется один раз.

Функциональность развивается постепенно.
