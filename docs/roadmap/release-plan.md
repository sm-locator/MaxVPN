Правила планирования релизов
1.

Каждый релиз должен иметь одну главную цель.

Не десять.

Одну.

2.

Любая новая функция проходит три проверки.

Она вписывается в архитектуру?

↓

Да

Она нужна именно в этом релизе?

↓

Да

Она делает продукт полезнее уже сейчас?

↓

Да

Только после этого она попадает в Release Plan.

3.

Никакая функция не реализуется только потому, что "её можно сделать".

Каждая функция должна решать реальную задачу пользователя.

4.

После каждого релиза следует этап использования продукта.

Именно практический опыт определяет содержание следующей версии.

Definition of Done

Релиз считается завершённым только тогда, когда выполнены все условия:

код реализован;
тесты проходят;
документация обновлена;
CHANGELOG заполнен;
GitHub Release опубликован;
система установлена на Brume 3;
основной сценарий использования успешно проверен.


Product Development Philosophy
Мы проектируем систему на годы вперёд, но выпускаем полезные версии как можно раньше.
